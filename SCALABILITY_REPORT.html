01

The bottom line

Is OyeChats scalable enough for production traffic today? Yes — with conditions. The engineering is careful: Redis-backed rate limiting, strong webhook idempotency, bounded conversation history, an HNSW vector index, and event-loop offloading of the heavy RAG work are all already in place. At current load the box sits at load average 0.08 with zero 5xx in 24h and zero restarts in 48 days — it is using well under 1% of its own ceiling.

But the architecture is single-everything on one shared droplet, pinned to one worker by design, with two ceilings that bite well before "big" traffic: a structural concurrency limit of ~15 simultaneous AI chats (the DB pool, held for the whole LLM generation), and a latent data-growth limit — the two hottest queries sequentially scan tables that grow forever. Both are cheap to fix and neither is a problem today.

Verdict
READY WITH CONDITIONS — ready for continued organic growth; not ready for a traffic surge, a single high-volume customer, or a second instance until the P1 items land.

Architecture at a glance

Topology

One DigitalOcean droplet — 2 vCPU / 4 GB — runs the API, PostgreSQL 16 + pgvector, Redis, the ARQ worker, and nginx all co-resident. FastAPI + SQLAlchemy 2.0 with a synchronous engine; React admin SPA + an embeddable widget. Measured

The master constraint

The API runs one gunicorn worker on purpose: the live-chat WebSocket manager holds socket state in-process, so multi-worker would split visitor/operator pairs. Everything about capacity flows from this single-worker, single-pool shape. Config-derived

Doc drift caught
DEPLOYMENT.md still states "1 vCPU / 2 GB". The live droplet is 2 vCPU / 4 GB — it was upsized. The DB is only 22 MB today (527 doc chunks, 63 sessions): an early-stage dataset, so all row-scaling risk is projection, not current pain.

The measured chat-concurrency knee

A controlled k6 test drove concurrent chat conversations through the real RAG pipeline against an isolated stack with a mock LLM (no external spend) and the production pool config. Postgres connections track concurrency, then plateau hard at the pool ceiling — and latency cliffs there. This is application capacity, independent of any LLM provider.

Database at scale — the missing indexes

Confirmed on the live production DB via EXPLAIN and re-measured on a seeded 1.1M-row copy: the two hottest queries sequentially scan tables that grow forever. Free at today's 63 rows; a linear-growth landmine. Adding the indexes is a trivial, safe migration.

Hot queryRowsBefore (no index) After (indexed)Speedup
Chat history session_id → LIMIT 5 1.1 M20.59 ms0.035 ms588×

Measured The unindexed history read runs on every chat turn and degrades linearly (4.3 ms → 20.6 ms as rows grew 100K → 1.1M); the indexed version stays flat at ~0.03 ms at any size. At 10M rows the seq scan would be ~200 ms per turn.

07

Recommended fixes, by impact

Add the two hot-path indexes P1 · trivial

chat_messages(session_id, created_at) and chat_sessions(bot_id, created_at). A measured 144–588× on the hottest queries; cheap now at 22 MB. CREATE INDEX CONCURRENTLY.

Stop pinning a DB connection across LLM generation P1

Make the chat-stream DB path async (or offload every sync call) and shorten the session's lifetime. This lifts the concurrency ceiling off the 15-connection pool — the single biggest lever.

Add global concurrency & backpressure P1

Cap the AnyIO threadpool to the pool size (or enlarge the pool) and add an in-flight ceiling so a spike sheds load gracefully instead of exhausting the pool and starving background jobs.

Remove horizontal-scaling blockers P1

Move the WebSocket ConnectionManager to a Redis pub/sub backplane and route uploads to R2/S3 instead of local disk — prerequisites for ever running a 2nd instance.

Harden the AI & ops path P2

LLM concurrency semaphore + per-bot spend ceiling + circuit breaker; a separate high-priority ARQ queue; cache auth lookups; install pg_stat_statements and tune Postgres for 4 GB.

08

Production readiness

READY WITH CONDITIONS

Evidence for "ready": live, stable, zero 5xx in 24h, zero restarts in 48 days, load average 0.08, correct indexes on the vector/full-text hot path, strong idempotency and rate limiting, bounded history — running comfortably at >99% headroom.

The conditions: single-worker / single-instance / single-DB / single-Redis by design, with documented horizontal-scaling blockers, a ~15 concurrent-AI-chat ceiling, and two missing hot-path indexes that turn data growth into latency. Ready for continued organic growth; not ready for a surge, a high-volume customer, or a second instance until the P1 items land.

Methodology. Repository-wide static analysis of app/ and api/; read-only inspection of the live production droplet (hardware, Postgres, Redis, nginx logs); and a controlled k6 load test against an isolated local stack with a mock LLM/embeddings server.
Honesty of numbers. Every figure is labelled Measured Config-derived or Estimated. The knee test ran on a local Apple-silicon box with the production pool config — the knee location (15) and index speedups transfer directly; absolute latency/throughput are an upper bound on the droplet.
Safety. No load was generated against production; production access was strictly read-only; no real LLM spend (mock-LLM by default). Full test system and raw results live under load-tests/.
